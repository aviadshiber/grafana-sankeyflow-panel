# Deployment and signing

Use development mode and the Docker server for local iteration. A development
build and a first public catalog submission do not need a signature.

## First public submission

1. Confirm the immutable plugin ID, version, minimum Grafana version, and `dist/` contents.
2. Run typecheck, tests, lint, build, React compatibility scanning, end-to-end tests, and the plugin validator.
3. Create a public GitHub release containing the packaged ZIP and SHA1 file generated by the release workflow.
4. In Grafana's Plugins Admin page, submit the ZIP URL, SHA1, public source repository, testing guidance, and provisioning status.
5. Wait for Grafana's review and signature-level assignment. Do not attempt to sign a public plugin before that approval.

## Approved public releases

After Grafana grants a signature level, create a Grafana Cloud Access Policy
token in the matching organization with the `plugins:write` scope. Store it as
the GitHub Actions secret `GRAFANA_ACCESS_POLICY_TOKEN`; never commit it or put
it in plugin configuration. The tagged release workflow passes that token to
Grafana's build action, which packages and signs the release. For a manual
release, export the token through a secret-aware shell and run `npm run sign`
after `npm run build`.

Keep signing credentials out of shell history and logs. Re-check the official
Grafana publishing and signing documentation when the signature level,
publisher identity, or catalog process changes. Treat a failed signature as a
release blocker; never bypass verification by editing generated metadata or
globally disabling signature checks.
